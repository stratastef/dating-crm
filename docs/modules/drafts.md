# Drafts

Routes are in `app/drafts.py`; the table is `drafts` (one row per draft).

| Route | Does |
| --- | --- |
| `POST /cards/{id}/drafts` | Have Claude write a draft for the card and store it. `kind` is `opener` when the card has no messages, else `reply`. |
| `PATCH /drafts/{id}` | Store the user's edit. Body: `{"edited": "..."}`. |
| `POST /drafts/{id}/send` | Send, or Retry a `failed` draft: queue the draft for the worker to send in 5 seconds (`UNDO_WINDOW`). Send at: with the optional body `{"send_at": "<timestamp with zone>"}`, at that time instead (a scheduled send). Returns `202` and the draft. In `app/send.py`. |
| `POST /drafts/{id}/undo-send` | Undo of a Send whose job has not started: the draft is `pending` again, its edit kept, and its job is cancelled. Returns the draft. `409` once the worker has claimed it (the detail names the status: "the draft is sending"). In `app/send.py`. |
| `POST /drafts/{id}/send-now` | Send now on a planned send: its job is cancelled and the draft queued again through `queue_send()`, to go out at once as the user's send. Returns `202` and the draft. `409` for what Send refuses, and once the worker has claimed it. In `app/send.py`. |
| `POST /drafts/{id}/hold` | Hold on a planned send: the same as `undo-send`. The draft is `pending` again, so it waits in Review, and its job is cancelled. In `app/send.py`. |
| `POST /drafts/{id}/unschedule` | Cancel of a scheduled send: the same as `undo-send` (one function), named for a send with a time. |
| `POST /drafts/{id}/copy` | Copy: the user took the text to send by hand. Moves a `pending` or `failed` draft to `copied`, on any card. `409` from any other status. In `app/review.py`. |

- A draft is `{"id", "card_id", "kind", "status", "original", "edited", "guardrail", "hot_lead", "sendable", "send_at", "timing_reason", "created_at"}`. `send_at` and `timing_reason` are its send time and why (see "Send timing"); `send_at` is null on drafts written before send timing. `created_at` is when it was written: a planned send's ring drains from it to `send_at`. The card docks the first of its draft list (`drafts` on every card) in the app's composer (see "Cards and messages", On the phone). `original` is Claude's text and never changes; `edited` is `null` until the user edits. The text to use is `edited` if set, else `original`.
- **Send or Copy** (ADR 0003): `sendable` says whether the app can send the draft now: its card is linked to a match (`external_id`) on an app whose connector works and is not copilot-only (`refusal()` in `app/send.py`, without the guardrail). The app offers Send when it is true and Copy when it is false. Every route that returns a draft builds it with `present(db, user_id, rows)` in `app/drafts.py`, which adds `sendable`; build yours the same way.
- `status` is `pending` until the user sends, copies or dismisses the draft (see "Review queue"). A sent draft is `approved` (queued; Undo puts it back to `pending`), then `sending` (the worker is sending it) and `sent` or `failed` (Retry puts it back to `approved`). A copied draft is `copied`, then `sent` once a message from the user newer than the copy (`copied_at`) is stored on its card, by sync, screenshot import or `POST /cards/{id}/messages` (`insert_message()` in `app/cards.py`). A dismissed draft is `dismissed`: dismiss also clears a `copied` or `failed` draft. v1 drafts left `approved` that were never sent were moved to `copied` by migration `t56_copied_drafts`; the app no longer calls `/approve`, which is gone.
- **Send:** the route answers `409` with the reason and queues nothing when the draft is not `pending` or `failed`, the app has no connector, the card has no `external_id`, or `send` is unavailable (see "Connectors": not declared, switched off, copilot-only, no token). Retry is the same route on a `failed` draft, so it passes the same checks.
- **Undo send:** the user's Send queues its job `UNDO_WINDOW` (5 seconds) later. Until the worker claims the draft (`approved` to `sending`), `undo-send` takes it back; after that it is refused and the message goes out once. Sends autopilot makes alone wait for their send time instead (see "Send timing").
- **Send at (a scheduled send):** a Send with `send_at` queues its job at that time exactly: no Undo wait, and none of the send-time bounds (the user's chosen time is used as given, even inside the night window or past 12 hours). The time becomes the draft's `send_at`. The draft stays `approved` until then, on the card as `scheduled_send` (see "Cards and messages"), and `unschedule` makes it `pending` again, back in Review. A naive timestamp is `422`. The job passes the same checks as any Send when it runs; a pause does not hold it. The SQL condition for "this draft is a scheduled send" is `SCHEDULED` in `app/drafts.py` (`queue_send(scheduled=True)` marks the job). A new message from the match does not drop it (it drops autopilot's planned sends only).
- **Queue a send from code:** `queue_send(db, user_id, draft_id, trigger, run_at=None, scheduled=False)` in `app/send.py` is the one way to send a draft. `scheduled=True` makes it a scheduled send, with `run_at` as the draft's `send_at`. It moves a `pending` or `failed` draft to `approved` and queues a `send_draft` job in your transaction, to run at `run_at` or at once; it returns the draft, or `None` if the draft is in another status. `trigger` goes to the audit log. A tap is not held by a pause or the autonomy level: both stop autopilot only, so the user can always send a draft they have read. A send no user asked for must pass `unattended=True`: see "Chat autopilot".
- **Take a queued send back from code:** `cancel_send(db, user_id, draft_id)` in `app/send.py`, next to `queue_send()`. It moves an `approved` draft back to `pending` and marks its queued `send_draft` job `skipped`, so a send queued again does not go out at the old time. It returns the draft, or `None` if the job has claimed it. A job a worker is already running is not waited for: it finds the draft `pending` and sends nothing. Use it for any later send that can be called off, such as a planned send.
- **Guardrail and the tap:** the user's tap sends a draft with a guardrail hit, because the guardrail's job is to put the draft in front of them. The one exception is `denies_ai`: such a draft is never sent, by a tap (`409`) or the job, until the user edits it and the guardrail runs again. Copy does not check the guardrail; the app shows why and offers neither Send nor Copy until the user edits it (see "Review queue", On the phone).
- **The `send_draft` job** sends the text (`edited` if set, else `original`) with the connector's `send`, stores the message on the card under the app's message ID (so sync does not add it twice), marked `sent_by_autopilot` when the send was unattended (autopilot sent it alone; see "Cards and messages"), writes an audit log entry (`type: message`, `target: card:<id>`) and sets `sent`. If `send` became unavailable after the tap, nothing is sent and the draft goes back to `pending`.
- **At most once:** the job commits `sending` before it calls the app. If the app answers with an error, or the worker dies before the job commits, the draft ends as `failed` and is never sent again, because the message may have gone out. A `failed` draft whose message did go out appears on the card at the next sync. A failed send waits in the review queue as `failed_send`, where the user retries it (`POST /drafts/{id}/send` again), copies it or clears it. A failed send has released its calendar holds, so a retried offer of a time names slots that are no longer held.
- The prompt holds the style profile, the preferences in force (`current_preferences()`: wishes, must-haves, dealbreakers), the card's app, name and notes, the match read (its `tone` sets the draft's tone), the conversation, and `similar_chats()` as examples.
- **Claude's reply** is JSON, read into `DraftReply` in `app/drafts.py`: `message` (the draft's text), `topic` (what the chat is about in a few words, stored on the card as its `topic`; an empty one keeps the card's topic), and `adjustment` and `timing_reason` for the send time (see "Send timing"). One call gives them all, so they cost nothing extra. To have the same call give more, add a field to `DraftReply`, ask for it in `_SYSTEM`, and read it in `draft_for()`. A reply that is not that shape stores nothing and is a `502`, so a broken reply is never sent as a message.
- **Offering a time:** every draft that offers a slot holds it, in every autonomy mode. When the match's unanswered messages hit `logistics`, no slot is held for the card yet and the calendar is connected, `draft_for()` tells Claude to name no day or time and adds the sentence from `calendar.offer_slots()`, which holds each slot it names for that draft. Without a connected calendar the draft offers nothing by itself; a time Claude or the user writes into the text is not held. `POST /drafts/{id}/dismiss` and a failed send release the draft's holds.
- The write route returns `409` until the style profile is written, and `502` if Claude's reply is not a `DraftReply` or its message is empty. Other code calls `draft_for(db, user_id, card_id)`, which raises `CannotDraft` in those cases (its `status` is the route's answer); a job catches it and never sees an `HTTPException`.
- A draft also has `guardrail` and `hot_lead`, the results of its Jev checks (see below).
